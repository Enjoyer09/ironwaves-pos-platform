## Railway Deploy Fix — Migration Crash
- Railway deploy failed healthcheck: `/health/deep` never responded (503 → "1/1 replicas never became healthy")
- Root cause: `backend/alembic/versions/20260819_0001_add_tenant_branches.py` used SQLite-only `randomblob()`/`hex()` functions in the backfill INSERT — these don't exist in PostgreSQL (Railway uses PG)
- The migration crashed during `alembic upgrade head` in the Docker CMD, so uvicorn never started, so the healthcheck endpoint never came up
- Fix: Added dialect check (`conn.dialect.name == "postgresql"`) — PG path uses `gen_random_uuid()` + `NOW()` + `CREATE EXTENSION IF NOT EXISTS pgcrypto`; SQLite path keeps `randomblob()` + `datetime('now')`
- Committed and pushed fix (commit 846028a2) — Railway will auto-rebuild

## Railway Deploy Fix — Attempt 2 (still failing after first fix)
- First fix (gen_random_uuid + pgcrypto) didn't work — deploy still failed healthcheck
- Possible cause: first failed deploy left `tenant_branches` table half-created (table exists but migration version not recorded → second run tries to create table again → crash)
- Also: `CREATE EXTENSION` may fail if Railway PG user lacks superuser privileges
- Also: `server_default=sa.text("1")` for boolean may not work in PG (needs `true`/`false`)
- Fix 2: Complete rewrite of migration to be fully idempotent:
  - Use `sa.inspect()` to check if table already exists before creating
  - Use Python `uuid4()` instead of any SQL UUID function (no pgcrypto needed)
  - Parameterized INSERT with bound variables
  - Boolean defaults: `true`/`false` for PG, `1`/`0` for SQLite
  - Skip backfill if rows already exist
